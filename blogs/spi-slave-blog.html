SPI Slave Register Interface — From Bugs to ASIC-Ready RTL

How I designed a 16-bit SPI slave to program registers on an ASIC, debugged five simulation bugs, fought an FPGA race condition, and hardened the whole thing for tape-out. All without a system clock.

Why an SPI Slave?

The problem was simple: I needed an external microcontroller to write configuration data into five 8-bit registers on an ASIC, and I wanted to minimize pin count. SPI gives you a full register programming interface with just four wires — SCLK, MOSI, MISO, and CS. No system clock needed on the slave side. The master's SPI clock drives everything.

The SPI slave sits at the boundary of the ASIC. An STM32G474 acts as the master, writing configuration values that downstream logic consumes through dedicated output ports.

Protocol & Frame Format

Each transaction is exactly 16 bits, clocked in SPI Mode 0 (CPOL=0, CPHA=0). The master holds CS low for the entire frame:

Bit 15 R/W
Bits [14:8] Address [6:0]
Bits [7:0] Data [7:0]

R/W = 1 means write — the master sends data on MOSI during clocks 9–16, written to the addressed register. R/W = 0 means read — the slave drives the register contents on MISO during clocks 9–16. Both complete in a single 16-bit transaction.

The Initial Code — Five Bugs

The starting Verilog had five issues that needed fixing before it could even pass simulation.

Bug 1: Inverted R/W Polarity

Bug

The spec defined bit 15 as R/W̄ — 1 = Read, 0 = Write. The code had it backwards, treating rw_bit == 1 as write.

Bug 2: MISO During the Wrong Phase

Bug

MISO data was being driven during clocks 1–8 (the address phase) instead of clocks 9–16 (the data phase). The master was sampling garbage.

Bug 3: Late tx_buffer Load

Bug

The transmit buffer was loaded on posedge cs — the end of the transaction. For a same-transaction read, the data must be available before clock 9.

Fix — Predictive Load

At bit_count == 7 on posedge sclk, reconstruct the address from shift_reg[5:0] (addr[6:1]) and the live mosi wire (addr[0]). This loads tx_buffer at posedge 8, making it available by negedge 8 when MISO output begins.

spi_slave_memory.v Verilog 
always @(posedge sclk or negedge rst_n) begin
    if (!rst_n)
        tx_buffer <= 8'h00;
    else if (!cs && bit_count == 5'd7 && !shift_reg[6]) begin
        if ({shift_reg[5:0], mosi} < MEM_DEPTH)
            tx_buffer <= reg_file[{shift_reg[5:0], mosi}];
        else
            tx_buffer <= 8'hFF;
    end
end

Bug 4: Combinational MISO Glitches

Bug

MISO was driven by always @(*) — a purely combinational path. In SPI Mode 0, MISO must be registered on negedge sclk to be stable when the master samples on the next rising edge.

Bug 5: Redundant Counters

Bug

Two separate counters (bit_count and miso_cnt) tracked the same frame progress on different clock edges. A single bit_count on posedge sclk is sufficient for both shift-in and shift-out logic.

After these five fixes, all 14 checks passed in Icarus Verilog simulation.

FPGA Prototyping — The Race Condition

The design was loaded onto a Basys 3 (Artix-7 XC7A35T) through PMOD JA, with the STM32G474 wired as the SPI master. The first hardware test results were... not great:

Test Result
addr 0x00 readgot 0x00, expected 0xA5 — FAIL
addr 0x02 readgot 0x0C, expected 0x0F — FAIL
addr 0x03 readgot 0x01, expected 0x81 — FAIL

Every read-back was wrong. The simulation passed perfectly, but hardware disagreed.

Root Cause

The memory write block triggered on posedge cs and checked bit_count == 16. But the bit counter also triggered on posedge cs, asynchronously resetting bit_count to zero.

In simulation, Verilog's non-blocking assignment semantics guarantee that both blocks see the old value of bit_count at the same posedge cs. On real FPGA hardware, the asynchronous reset path through the clear pin of the bit_count flip-flops is faster than the clocked data path to the memory-write logic. By the time the memory-write block evaluates bit_count, it's already been forced to zero.

Key Insight

This is a classic simulation-versus-hardware mismatch. The simulator is right according to the language spec. The hardware is right according to physics. They don't agree, and physics wins.

The Fix

Move the memory write to fire on the 16th rising edge of SCLK (detected as bit_count == 15 pre-NBA), reconstructing the frame from shift_reg[14:0] and the live mosi wire:

spi_slave_memory.v Verilog 
always @(posedge sclk or negedge rst_n) begin
    if (!rst_n) begin
        for (i = 0; i < MEM_DEPTH; i = i + 1)
            reg_file[i] <= 8'h00;
    end else if (!cs && bit_count == 5'd15) begin
        if (shift_reg[14] && shift_reg[13:7] < MEM_DEPTH)
            reg_file[shift_reg[13:7]] <= {shift_reg[6:0], mosi};
    end
end

This eliminated the dependency on posedge cs entirely. After this fix, all 17 firmware tests passed on hardware.

ASIC Hardening — The Hard Part

A design that works on FPGA doesn't automatically work in an ASIC flow. The FPGA-proven code had four structural issues that would cause failures during synthesis, STA, DFT insertion, or physical design.

Issue 1: cs Used as Asynchronous Reset

In the FPGA version, posedge cs appeared in sensitivity lists for the bit counter, shift register, and MISO output. ASIC synthesis tools would route cs through a reset tree, but since cs transitions asynchronously relative to sclk, recovery and removal timing checks would fail.

Issue 2: Multiple Clock Edges

posedge sclk and negedge sclk are two separate clock domains in ASIC timing analysis. Every signal crossing between them gets flagged as a CDC violation, and CTS would need two independent clock trees from the same pin.

Issue 3: Scan Testability

With cs acting as both a data input and an asynchronous reset simultaneously, DFT scan chains can't properly shift through the affected flip-flops.

Issue 4: Glitch Sensitivity

FPGA routing gives clean, glitch-free paths. On ASIC, any runt pulse or coupling-induced glitch on cs would corrupt bit_count.

The Dead End: Going Fully Synchronous

My first instinct was to make everything synchronous — sample cs on posedge sclk using a delayed copy for edge detection, and use an active flag to track frame boundaries.

This failed fundamentally. In SPI Mode 0, SCLK idles low between transactions. With no clock edges between frames, the synchronous logic never sees cs go high and then low again. The bit counter stays stuck at 16, and all subsequent transactions fail.

The Correct Solution

Apply cs as an asynchronous clear to bit_count only. Not as a general-purpose reset for all logic:

spi_slave_memory.v Verilog 
// cs clears ONLY bit_count — safe because SPI protocol
// guarantees cs transitions only while sclk is idle (low)
always @(posedge sclk or posedge cs or negedge rst_n) begin
    if (!rst_n)
        bit_count <= 5'b0;
    else if (cs)
        bit_count <= 5'b0;
    else if (bit_count < 5'd16)
        bit_count <= bit_count + 1'b1;
end

This is safe because SPI Mode 0 guarantees that cs only transitions while SCLK is idle (low). There's no simultaneous clock edge to race against, so recovery/removal timing is inherently met.

All other blocks sample cs as synchronous data on posedge sclk. Only rst_n serves as the global async reset. The single negedge flop (MISO output) gets a scan-mode mux for DFT — standard practice.

Final Architecture

The RTL ended up with five cleanly separated always blocks:

Properties that matter: single clock source (only the MISO flop uses the inverted edge), single global async reset, targeted async clear on bit_count only, no combinational outputs, no system clock dependency, and clean named output ports for downstream ASIC logic.

Firmware Test Harness

The STM32G474 firmware mirrored every simulation test on real hardware. Seven test categories, 17 total checks:

  1. Write all 5 registers with distinct patterns
  2. Read back and verify each register via MISO
  3. Overwrite one register, verify others untouched
  4. Read out-of-range addresses (expect 0xFF)
  5. Write to out-of-range, verify no corruption
  6. Write and read 0x00 (zero vs. default)
  7. Hardware reset via GPIO, verify all registers cleared

All 17 passed on the final RTL.

What I Learned

Passing simulation is necessary but not sufficient. Each target platform — behavioral simulation, FPGA, ASIC — imposes additional constraints that only surface through targeted analysis and testing at each level.

The FPGA race condition was invisible to simulation because Verilog's event scheduler is deterministic where hardware isn't. The ASIC design-rule violations were invisible on FPGA because FPGAs don't care about clock-tree synthesis or scan chains. And the "fully synchronous" approach that seemed obvious turned out to be a dead end because of a fundamental property of SPI Mode 0 — SCLK idles low, so there are no edges between transactions.

The final design works at all three levels simultaneously. That was the real goal.
